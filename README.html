job-runner

One wrapper for every scheduled job on my machines (MacBook, NAS, GCP): a library of helpers to decide when to skip, standard statuses, everything on one phone dashboard. · In production since 2026-10-10 · Updated 2026-10-12 (verified against the NAS's ~/opt/job-runner/ that day)

1 · The big picture: every machine reports to the NAS

A trigger starts a job's entrypoint, which sources the library; each check writes its status here and copies it to the NAS, where the dashboard reads every machine's statuses.

MacBook NAS BabisNAS GCP GitHub ── statuses (SSH or own disk)   - - - git (job-runner-sync)

2 · How job-runner gets onto each machine

Like every repo: a clone, then bash install.sh. The script recognises the NAS by its machine name and adds the gate and the dashboard there.

What a reinstall replaces, and what it never touches (~/opt/job-runner/)

~/opt/job-runner/
├── lib.sh  ops.sh  put-conf.sh       the library and its operations
├── gate.sh                           NAS only: what job-runner's keys may run

3 · A job's dashboard settings: every case

A job's settings (its title, its order, when it turns red…) live in its own project, beside its entrypoint. The project's install.sh deploys the file to ~/opt/<repo>/, then calls put-conf.sh, which gives it to the dashboard on the NAS.

A · The job runs on the NAS

One file, on one disk: the dashboard reads the project's own file through a symlink.

B · The job runs on the Mac only

Nothing of this project is on the NAS, so its file travels like its statuses do: a copy over SSH, through the gate.

C · The job runs on the Mac and the NAS

The NAS's install makes the symlink (as in A). The Mac's install also sends a copy, which is refused: kept: linked on the NAS.

D · The job runs on GCP

As B. No GCP job has settings today (auto-commit uses the defaults).

E · The job is decommissioned

One ssh command on the NAS, no repo and no install (the skill jobs-and-services has it). If the job comes back, its install gives its file again.

F · The project left the NAS, the job was not decommissioned

The dashboard shows a yellow line, links to a missing file, until the job is decommissioned (E).

4 · The repo

job-runner/
├── AGENTS.md  REQUIREMENTS.md        rules and words for agents · what the user gets
├── DESIGN.md  CONSIDERATIONS.md      what is built and why · what is still unclear
├── install.sh  uninstall.sh          install on this machine (section 2) · remove it, keeping the data
├── lib.sh                            the library, sourced by every entrypoint
├── ops.sh                            the 7 operations on an env's folder (put-status, put-log, put-conf, …)
├── gate.sh                           the NAS's gate: job-runner's keys may run only ops.sh
├── put-conf.sh                       gives a job's settings to the dashboard (section 3)
├── dashboard/                        dashboard.py; conf/: the defaults and the canaries' settings
├── canaries/                         fake jobs testing each promise in real conditions
├── doc/examples.md                   every current job's entrypoint, in its own project
├── skills/jobs-and-services/         the skill for creating, changing and removing jobs and services
├── deploy/keys/                      job-runner's public keys, one per machine, for the gate
├── test/                             lib_test.sh, examples_test.sh, dashboard_test.py, gate_test.sh
└── todo.html                       open work, in Todoist
